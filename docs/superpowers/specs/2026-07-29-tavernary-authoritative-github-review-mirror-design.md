# Tavernary-Authoritative Intake and GitHub Review Mirrors

## Status

Approved in sections on 2026-07-29, then reconciled against the completed
Source-Backed Multi-Card Registry and Catalog Tag System schema-v6
implementations.

## Summary

Tavernary will be the authoritative authoring surface for every public
submission, maintenance request, and Help ticket. GitHub will remain the
identity, issue-creation, automation, review, and audit surface, but its Issue
Forms will be presented as generated review mirrors rather than a second
authoring mode.

Every public request will:

1. begin in Tavernary;
2. validate in Tavernary;
3. show a complete Tavernary review;
4. open a generated GitHub review mirror in a new tab;
5. leave the populated Tavernary form and review available; and
6. direct corrections back to Tavernary, where reopening GitHub regenerates
   the mirror from current form state.

The generated domain manifest is the sole payload authority for automation.
GitHub titles and readable Issue Form fields are presentation only. Differences
between readable fields and a valid manifest do not block, reject, close, or
change a request.

GitHub Issue Forms do not provide a supported read-only input state. This
design therefore uses explicit review-only guidance and manifest authority
instead of attempting a brittle simulated lock. It encourages contributors to
correct requests in Tavernary without denying normal issue creation.

## Context

The reported Project Type defect is a concrete example of why GitHub cannot be
the authoring authority. Tavernary currently starts public project intake as
Frontend and immediately opens GitHub without a Tavernary review. GitHub may
also restore URL-prefilled Issue Form values after the contributor edits them.
A contributor can therefore believe they changed Project Type while the
readable GitHub field returns to Frontend.

The completed schema-v6 and Multi Projects work makes the same boundary more
important:

- ordinary project intake uses project-submission manifest version 4;
- cards use schema version 6 and reference canonical `source_id` records;
- owner maintenance uses owner-request manifest version 2;
- one owner manifest may contain up to ten complete add-card drafts;
- summary and tag requests carry independent automatic/manual intent;
- card retirement is soft and reversible;
- source delisting is repository-wide and permanent; and
- exact fingerprints and vocabulary hashes protect stale publication.

Those contracts are too rich to reconstruct safely from editable GitHub
readable fields. The completed implementations are the baseline this design
must preserve, not work that this design needs to repeat.

## Goals

- Make Tavernary the only advertised starting point for public intake.
- Give every public flow an explicit Tavernary review before GitHub opens.
- Fix Project Type by requiring a deliberate Tavernary selection and retaining
  it through review and handoff.
- Preserve form, review, Kit draft, and multi-card draft state after handoff.
- Give clear, accessible feedback while GitHub opens and after it has opened.
- Let contributors return to Tavernary, edit, and regenerate a fresh mirror.
- Use each domain's generated manifest as the only automated payload.
- Treat GitHub-readable differences as harmless presentation drift.
- Keep missing or damaged manifest issues open with recovery guidance.
- Preserve static-first operation without accounts, OAuth, or a runtime
  backend.
- Perform a regression pass across all key desktop and mobile submission
  interactions.

## Non-goals

- Adding a Tavernary account system or submission database.
- Detecting whether the contributor actually created or canceled the GitHub
  issue after the new tab opens.
- Cryptographically proving that a manifest was generated by Tavernary.
- Preventing a determined user from editing fields GitHub itself exposes.
- Reimplementing schema v6, the Goals-and-Traits taxonomy, source records, or
  Multi Projects.
- Changing existing owner/staff authority, automatic metadata generation,
  exact-file publication, or stale-fingerprint rules.
- Redirecting private security reports into public issue intake.
- Adding a second direct-GitHub authoring mode.

## Scope

The contract applies to every public issue-backed flow:

### Project submission

- new Frontend, Extension, or System Preset submission;
- project-submission manifest version 4;
- automatic/manual summary and tag requests;
- existing controlled compatibility and additional-context fields.

### Project and source maintenance

All six owner-request manifest version-2 operations:

- edit card details;
- add cards from this source;
- retire this card;
- restore this card;
- update repository location; and
- permanently delist this source.

The design preserves the distinction between a card and its source. Source
location is changed once on the source record, not copied across cards.
Permanent source delisting remains the destructive, repository-wide operation
that hides every sibling card and reserves the immutable repository identity.

### Kits

- create a Kit;
- edit a Kit;
- withdraw a Kit; and
- report a Kit.

Kit withdrawal moves from its current direct GitHub link to a Tavernary
confirmation and review flow with a versioned manifest.

### Help

- report a project;
- report a website problem;
- report a Kit;
- submit a general Help request; and
- other future public Help forms using the same issue-backed contract.

Private security reports remain on GitHub's private security-advisory surface.

## Baseline Contracts to Preserve

### Project submission manifest v4

The current v4 manifest remains the source for:

- `project_type`;
- `primary_function`;
- `source_url`;
- known and proposed frontend compatibility;
- frontend independence;
- additional context;
- automatic/manual summary request and conditional value;
- automatic/manual tag request and conditional controlled IDs; and
- Preset model-family and completion-format compatibility.

This handoff change does not require a new manifest version unless
implementation discovers a genuine payload change. Review state and
new-tab-opening state are browser concerns, not manifest data.

### Schema-v6 cards and source records

New and edited cards continue to use:

- `source_id`, not an inline source object;
- zero to six controlled Goal/Trait tags;
- independent `metadata_policy.summary` and `metadata_policy.tags`;
- card-owned `listing_status`; and
- source-owned repository identity, refresh, snapshot, and permanent delisting.

The public project form continues deriving ordinary community-submission names
from source evidence. It does not reintroduce an editable display-name field.

### Owner-request manifest v2

The owner form continues generating complete operation-specific manifests:

- card operations retain project fingerprints;
- source operations retain source fingerprints;
- tag-bearing operations retain the tag-vocabulary hash;
- add-card requests retain one to ten complete proposed cards;
- add-card drafts retain independent summary/tag modes;
- automatic modes do not inherit manual provenance;
- source moves retain immutable repository identity checks; and
- source delisting retains its typed repository-wide confirmation.

The shared handoff layer must pass these manifests through unchanged. It must
not flatten them into a generic card edit or rebuild them from readable GitHub
fields.

### Existing authority and publication

GitHub issue-author identity remains the authority input. Personal repository
owner and trusted Tavernary editor rules are unchanged. Add-card batches remain
manual-merge operations; other eligible owner operations retain their existing
publication behavior.

The new transport contract does not weaken exact-head, exact-file-set,
fingerprint, vocabulary, concurrency, or source-lock validation.

## Tavernary Authoring and Review

Every in-scope flow has three explicit Tavernary stages:

```text
editing -> reviewing -> handoff
```

The review stage shows the complete public request and offers:

- **Back and edit**;
- **Cancel**; and
- **Continue on GitHub**.

**Back and edit** restores focus to the authoritative field without clearing
values. **Cancel** exits review but does not silently discard persistent Kit or
multi-card drafts. Existing explicit discard controls remain the only way to
destroy those drafts.

### Project Type

Project Type begins unselected. The contributor must choose Frontend,
Extension, or System Preset before review.

Changing Project Type may continue resetting incompatible type-specific fields
under the existing validation contract, but typing a source URL, reviewing the
request, opening GitHub, or returning to edit must never change the selected
type.

The v4 manifest and Tavernary review show the same explicit value. GitHub's
readable Project Type field may drift without affecting automation.

### Rich owner and Kit state

Owner add-card review shows every proposed card, generated project ID,
automatic/manual metadata request, compatibility value, and controlled tag.
Returning to edit preserves the whole batch.

Permanent source-delisting review continues naming the source and every
affected sibling card. The typed confirmation remains part of the Tavernary
flow and owner manifest.

Kit create/edit review shows title, description, and complete project
selection. Opening GitHub no longer calls `discardDraft()`. The draft stays
available until the contributor explicitly discards it or replaces it through
normal Kit-builder actions.

Kit withdrawal begins from the selected Kit's **Request withdrawal** action and
routes to a Tavernary confirmation/review experience instead of directly to
GitHub. Its generated manifest includes the stable Kit ID and explicit
withdrawal confirmation. GitHub still verifies the issue author's durable user
ID against the canonical Kit author.

## Handoff Feedback

Selecting **Continue on GitHub** immediately enters an accessible
**Taking you to GitHub...** state and attempts to open the generated mirror in
a new tab.

The original Tavernary tab remains open and then shows:

> GitHub review opened in a new tab. Create the issue there, or return here to
> make changes.

It offers:

- **Back and edit**; and
- **Open GitHub review again**.

This is handoff feedback, not a false claim that GitHub issue creation
succeeded. Static Tavernary cannot observe whether the contributor selected
GitHub's create or cancel action.

Editing after handoff clears the prior opened confirmation. Reopening rebuilds
the manifest and readable mirror from current Tavernary state. It never reuses
stale prepared values.

## Handoff Recovery

A blocked popup or failed tab opening is non-destructive. Tavernary keeps the
review and all form state visible, explains the failure, and offers the
Tavernary-generated GitHub review URL again.

The recovery action is labeled as reopening the prepared review, not as a
direct GitHub fallback or alternate intake.

Where a complete mirror exceeds reliable URL-prefill limits, the existing
clipboard-assisted transport remains available:

1. Tavernary copies or presents the complete generated manifest.
2. GitHub opens the matching review template.
3. Tavernary instructs the contributor to paste the manifest unchanged.
4. The original Tavernary review and reopen action remain available.

This is transport recovery for an already-authored Tavernary request, not a
second authoring mode.

## Shared Handoff Architecture

All domains use one shared handoff controller and presentation contract:

```text
editing -> reviewing -> opening -> opened
                     \-> recovery
opened -> editing -> reviewing -> opening
```

The shared layer owns:

- opening state;
- new-tab opening and blocked-popup detection;
- safe URL-length handling;
- clipboard/prompt recovery;
- persistent opened and recovery feedback;
- edit and reopen transitions; and
- accessible status announcements.

Each domain continues to own:

- form state;
- validation;
- readable Tavernary review rows;
- versioned manifest construction and serialization;
- GitHub Issue Form template and readable prefill mapping; and
- domain-specific authority and automation.

Project, owner, Kit, withdrawal, and Help manifests remain explicit,
independently versioned contracts. No universal manifest is introduced.

The current project, Kit, and Help transports converge on the shared controller
without losing domain serializers. The shared controller must detect a blocked
popup consistently; the current project and Kit transports must no longer
report success when `window.open()` returns `null`.

## GitHub Review-Mirror Contract

Every public Issue Form is reframed as a Tavernary-generated review mirror:

- Its name and description say to begin in Tavernary.
- Opening guidance says the values were prepared by Tavernary.
- Guidance links to the exact Tavernary intake route for corrections.
- The generated manifest is visibly labeled as the automation payload.
- Readable fields are described as review-only.
- Blank issues remain disabled.
- The issue chooser uses Tavernary contact links for project, Kit, owner, and
  Help intake.
- Repository and Tavernary copy no longer advertises structured GitHub forms
  as an accessibility fallback.

GitHub fields remain technically editable because GitHub offers no supported
lock. The copy must be honest about that limitation without presenting editing
as a supported workflow.

Readable fields remain useful to contributors and maintainers. They may be
optional where GitHub allows so delayed prefill behavior cannot prevent issue
creation. The generated manifest field remains required in the corresponding
review template.

## Manifest-Only Automation

For new in-scope requests:

- a valid, supported domain manifest is the sole automated payload;
- titles and readable fields are never parsed into a substitute manifest;
- route labels may dispatch the correct workflow but do not supply payload
  values;
- readable differences are ignored;
- a valid manifest is not compared with readable fields for drift; and
- automation never asks the contributor to edit readable fields to retry.

Current readable fallback construction is retired, including:

- project-submission reconstruction from Project Type, URL, metadata-choice,
  and compatibility fields;
- owner-operation reconstruction from request type, card/source IDs, and
  proposed readable values;
- Kit withdrawal processing from Kit ID, share URL, and checkbox alone; and
- unlabeled route recovery that treats a complete set of readable headings as
  authoritative intake.

Compatibility for already-admitted historical transactions remains governed by
the existing cutover/recovery rules. This design does not invalidate a
previously admitted version solely because the public intake surface changed.

## Missing or Invalid Manifest Recovery

A missing, malformed, stale, or unsupported manifest does not trigger a
payload mutation and is not reconstructed from readable fields.

Automation:

- leaves the issue open;
- applies the existing `needs-information` equivalent;
- explains the manifest problem without alarming language;
- links to the exact Tavernary intake route; and
- tells the contributor to return to the still-open Tavernary tab, correct the
  request, and open a new review mirror.

Existing retry behavior may process a restored valid manifest when safe.
Missing or damaged manifests are not auto-closed merely because the contributor
started in the wrong place.

For destructive or stale operations, existing fingerprint, identity, source,
and vocabulary failures remain authoritative. The friendlier handoff contract
does not turn those safety failures into readable-field fallback.

## Accessibility

The opening, opened, and recovery states use announced status regions and do
not rely on color alone. Focus remains predictable when:

- review begins;
- the contributor returns to edit;
- a popup is blocked;
- clipboard fallback is required; or
- a previous review is regenerated.

All actions retain the repository's touch-target standards. Review content
remains usable at a 320-pixel viewport, including the six-tag picker and
ten-card owner batch added by the completed features.

Private or security-sensitive information warnings remain present before
public GitHub handoff.

## Failure Handling

- Domain validation failure: stay in Tavernary editing; create no mirror.
- Manifest normalization failure: stay in Tavernary review/editing; open
  nothing.
- Blocked popup: preserve state and offer the prepared review again.
- URL too long: preserve state and use unchanged-manifest clipboard recovery.
- Clipboard unavailable: present a copy prompt without clearing the review.
- Contributor edits after handoff: invalidate the prior opened confirmation and
  regenerate.
- Missing GitHub manifest: keep the issue open with Tavernary return guidance.
- Readable GitHub drift: ignore it.
- Stale card/source/tag/Kit state: retain the existing domain-specific safety
  response; do not reconstruct intent.
- Any transport failure: never discard a Kit or multi-card draft.

## Verification

Implementation follows test-driven development. Regressions are written before
behavior changes.

### Project submission

- Project Type begins unselected.
- Typing or changing the source URL does not change Project Type.
- Review and back/edit retain Project Type and every v4 field.
- Frontend, Extension, and Preset reviews serialize valid v4 manifests.
- Automatic/manual summary and tag requests survive review and reopen.
- GitHub-readable Project Type drift cannot change the parsed manifest.

### Owner and Multi Projects

- All six owner operations retain valid manifest-v2 payloads.
- Add-card batches of one and ten preserve all drafts through review and
  handoff.
- Summary/tag modes, tag-vocabulary hash, fingerprints, `source_id`, and typed
  delist confirmation remain unchanged.
- Returning to edit and reopening produces a new manifest from current state.
- The handoff refactor does not weaken manual-merge add-card behavior, source
  locks, stale checks, or exact operation paths.

### Kits

- Kit create/edit gains Tavernary review.
- Opening or reopening GitHub never discards the Kit draft.
- Explicit discard remains functional.
- Kit withdrawal routes through Tavernary and emits a valid versioned manifest.
- Withdrawal continues verifying the durable GitHub author identity.

### Help

- Every public Help route validates and reviews in Tavernary.
- Existing Help manifests remain valid and domain-correct.
- Private security reporting remains unchanged.

### Shared handoff

- Opening, opened, recovery, edit, and reopen transitions are deterministic.
- `window.open() === null` enters recovery for every domain.
- Oversized URLs use unchanged-manifest clipboard recovery.
- Failed clipboard access uses the copy prompt.
- Form and review state survive every failure path.
- Status announcements and focus behavior are accessible.

### GitHub and automation

- All public templates use consistent review-mirror guidance.
- Direct structured-fallback wording and links are absent.
- The issue chooser routes contributors to Tavernary intake.
- Valid manifests remain authoritative when every readable field differs.
- Readable differences never block, reject, close, or mutate a request.
- Missing/invalid manifests remain open with `needs-information` and return
  guidance.
- Project, owner, Kit, withdrawal, and Help readable fields cannot construct an
  automated payload.
- Historical admitted-version recovery remains covered.

### Full interaction pass

Run focused component, manifest, transport, parser, and Issue Form tests first.
Then run:

- the full repository check;
- static catalog/export verification;
- desktop end-to-end coverage for every public intake route;
- 320-pixel mobile end-to-end coverage;
- popup-blocked and oversized-manifest recovery cases;
- owner ten-card and six-tag stress cases; and
- Kit draft-persistence cases.

The existing stale mobile assertion expecting the intentionally visible Help
link to be hidden has already been corrected by the completed tag-system work
and must remain green.

A final approval-gated live GitHub smoke test may verify current Issue Form
prefill, delayed readable-field drift, Tavernary return guidance, and
manifest-only parsing without creating an unwanted public issue.

## Rollout

Implementation proceeds in reviewable stages:

1. Shared handoff controller, feedback presentation, and recovery tests.
2. Existing Help review integration.
3. Project review, deliberate Project Type selection, and v4 handoff.
4. Owner manifest-v2 integration across all six card/source operations.
5. Kit create/edit review and draft preservation.
6. Tavernary Kit-withdrawal form and manifest.
7. Remaining Help/report integrations.
8. GitHub Issue Form, chooser, contributor-copy, and manifest-only parser
   cutover.
9. Full desktop/mobile interaction pass and approval-gated live smoke.

The completed schema-v6/source-registry migration is a prerequisite baseline,
not a rollout step. No new catalog migration is required for this feature.

## Acceptance Criteria

- All advertised public intake begins in Tavernary.
- Every public request validates and reviews in Tavernary before GitHub opens.
- Project Type has no silent Frontend default and cannot be changed by GitHub
  readable-field resets.
- The original Tavernary tab visibly reports handoff and remains editable.
- Reopening GitHub regenerates the current request.
- Project v4, owner v2, Kit, withdrawal, and Help manifests remain
  domain-specific and authoritative.
- Completed schema-v6, tag, source, and Multi Projects rules remain intact.
- Kit and multi-card drafts survive handoff and recovery.
- GitHub is described as a review/create-or-cancel surface, not an editing
  surface.
- Readable GitHub drift is ignored.
- Missing or invalid manifests remain open with actionable Tavernary return
  guidance.
- No runtime backend, Tavernary account, or OAuth dependency is introduced.
- Focused, full, build, export, desktop, and 320-pixel mobile verification pass.

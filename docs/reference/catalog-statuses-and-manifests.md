# Catalog statuses and machine contracts

This document is the single reference for status labels and manifest outputs used by
the V1 catalog.

## Project catalog states

| Field | Values | Meaning |
| --- | --- | --- |
| `metadata_status` | `provisional`, `curated` | Editorial confidence in fact fields. Provisional can still be visible. |
| `sourceStatus` | `pending`, `healthy`, `stale`, `manual` | Derived runtime view of source freshness and source type constraints. |
| `visibility` | `published`, `quarantined`, `disabled` | Visibility gate for public cards. |
| `visibility_reason` | `null`, `identity-change`, `source-unavailable`, `removed`, `safety-review` | Required reason when visibility is not `published`. |
| `refresh_policy` | `automatic`, `paused` | Whether GitHub refresh continues automatically. |

### Source status derivation

- `pending`: no snapshot exists yet for a project that has a GitHub-type source.
- `healthy`: latest GitHub snapshot is current enough for normal card display.
- `stale`: source is temporarily unavailable/rate-limited; last known facts are retained.
- `manual`: source is not GitHub-managed (`url` presets and org sources), so freshness
  derivation is intentionally manual.

## License status and filters

| Internal status | Filter label | Meaning |
| --- | --- | --- |
| `osi-approved` | Open source | SPDX-resolvable OSI-approved license detected. |
| `proprietary` | Proprietary | License exists but is not OSI-approved. |
| `missing` | Missing license | No license detected from the source. |
| `pending` | Pending verification | License detection has not completed or is ambiguous. |

## Activity states

`activity.evidence_status` is rendered as `provisional`, `complete`, or `degraded`.

- `provisional`: baseline activity window is pending and weekly activity may be `N/12`
  placeholders.
- `complete`: stable 12-week activity graph available.
- `degraded`: baseline was attempted but cannot be fully validated as complete.

`active-weeks` display and dormant behavior:

- `Dormant` means source activity is not present for recent windows.
- `~N/12` may appear while evidence is provisional.
- `0/12` with evidence complete means no qualifying changes in the last 12 fixed
  weeks.

## Snapshot health impacts

`data/snapshots/github/*.json` exposes `source_health`:

- `healthy`: normal update path.
- `unavailable`: temporary failure, may render as stale with retained facts.
- `identity-change`: public source identity mismatch, removed from public catalog until corrected.
- `deleted` / `private`: removed from public catalog.

## Development filters

- `active-month` = source activity within the last 30 days.
- `new-release` = release or preset publication in the last 30 days.
- `dormant` = current dormant marker.
- `license=open-source` maps from `osi-approved`.
- `license=pending`, `license=proprietary`, `license=missing` map directly.

## GitHub refresh manifest (`data/snapshots/github-refresh.json`)

The refresh manifest is generated by `catalog:refresh` and must validate against
`data/schemas/github-refresh.schema.json` (`schema_version: 1`).

Top-level required fields:

- `schema_version`, `mode`, `started_at`, `completed_at`
- `counts`
- `api`
- `duration_ms`
- `project_timings`
- `snapshot_changes`
- `deployment_requested`

Manifest `counts` fields:

- `total`, `checked`, `changed`, `unchanged`, `provisional`, `degraded`, `unavailable`,
  `failed`, `compared`, `baseline`, `fallback`

`api` usage fields:

- `graphql_requests`, `graphql_points`, `graphql_remaining`, `rest_requests`

`project_timings` is per project with:

- `project_id`, `outcome`, `duration_ms`, `error_code`

Outcome enum:

- `unchanged`, `compare-source`, `compare-excluded`, `baseline`, `fallback`,
  `unavailable`, `identity-change`, `failed`

Interpretation:

- `unchanged`: no data change detected.
- `compare-source`: source observed and compared normally.
- `baseline`: baseline collection completed.
- `fallback`: clone or compare fallback path used.
- `identity-change` / `unavailable` / `failed`: visibility and retry implications apply.

`snapshot_changes` and `deployment_requested` are the high-level deployment gates for
automation (whether persisted snapshot writes and Pages deployment were requested for
the run).
